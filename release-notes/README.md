# Release notes

각 fork 릴리스마다 `v<MAJOR>.<MINOR>.<PATCH>.md` 파일을 하나씩 둔다.
태그 `vX.Y.Z` 를 push 하면 `.github/workflows/release-deurim.yml` 이
같은 이름의 파일 내용을 GitHub Release body 로 그대로 올리고,
인앱 "새 버전 안내" 다이얼로그도 같은 텍스트를 보여 준다.

해당 파일이 없으면 GitHub auto-generated PR 목록으로 폴백한다.

## 스타일

릴리즈 노트는 사용자가 그대로 읽는 글이다. 친근하고 쉽게 쓴다.

- **말투는 해요체(~요).** "수정했습니다"가 아니라 "수정했어요", "추가했어요"처럼 쓴다.
- **어려운 기술 용어는 빼고 쉬운 말로.** 클래스명·함수명·라이브러리·내부 구조 이름은 적지 않는다.
  예: "SoundPool로 전환" → "효과음이 끊기던 문제를 고쳤어요".
- **화면에 드러나지 않는 내부 오류 수정은 한 줄로 뭉뚱그린다.**
  사용자가 직접 보지 못한 버그는 자세히 풀지 말고 "○○ 오류를 수정했어요" 정도로만 적는다.
  예: "스케줄러의 'deck not found in limits map' 예외 처리" → "학습 일정이 가끔 어긋나던 오류를 수정했어요".
- 가장 위 한두 줄로 이번 버전이 무엇이 좋아졌는지 사람 말로 한 문장.
- `## 새 기능` / `## 개선` / `## 알아 둘 것` 같은 소제목 + 짧은 불릿.
- 사용자 입장에서 의미 있는 변화만 적는다. 내부 리팩터·lint·코드 정리는 생략.
- 길이는 한 화면 안에 들어올 정도가 보기 좋다.
